RETENTION / CAPACITY
Proposed lifecycle rules apply ONLY postgres/hourly/ (7d) and postgres/daily/ (30d).
Read and merge existing bucket lifecycle first. Never overwrite unrelated rules.
No script performs S3 deletes. No resume prefix belongs in backup lifecycle rules.
Check bucket versioning: expiration of current objects may leave noncurrent versions;
noncurrent expiration requires a separate approved rule. Historical legacy prefixes
remain untouched. Expiration is irreversible and not an exact wall-clock scheduler.
Restore-test every new backup plus monthly independently selected older snapshot.
Targets RPO<=1h/RTO<=4h remain goals until measured end-to-end recovery rehearsal.

Limits UNCHANGED: live database <50MiB, MemAvailable>3GiB, /tmp free>5GiB.
Scratch: CPU0.5, memory+swap768MiB, tmpfs384MiB, pids128, no network/ports, pullnever.
Archive also capped below50MiB; compressed size does not guarantee restored size.
Growing historical archives may exceed scratch capacity and fail; do not enlarge it
without measured resource review. Failure retains private files/container for diagnosis;
monitor disk/memory, investigate promptly, never docker-prune or broad recursive delete.
Current live capacity NOT measured this phase. Cannot certify1000 candidates from
row count alone: resume bytes live in S3 but extracted text/indexes/job history grow DB.
Before pilot measure pg_database_size baseline, synthetic100-profile delta, backlog
drain rate and restore peaks on isolated data. Estimate safe count as
floor((40MiB-baseline_bytes)/measured_bytes_per_profile), retaining10MiB guard margin.
Stop expansion at40MiB pending review; >=50MiB automated backups fail closed.
If baseline already>=40MiB, gate must be reviewed before launch, not after failure.
1,000 CVs at2MB each is ~2GB of S3 originals, NOT evidence the DB stays under50MiB.

recent failed jobs (updated within1h), cleanup backlog>24h, both filesystems>=80% or
free<=5GiB, memoryavailable<=max(1GiB,15%), independent backup/recovery freshness.
MainSQS total visible+inflight+delayed>100, oldestage>600s; DLQ total>0.
Nonemptyqueue with no fresh CloudWatch datapoint<=5min fails as unverified.
Queue metrics approximate/lag; thresholds need load rehearsal, no auto scaling.
Historical failures remain in DB; no mutating acknowledgement. A recent failure
ages out after1h: recovery notification explicitly does NOT mean the job was repaired.
Operator must review every failure; monitor outage>1h may miss that event. Independent
monitor heartbeat/missing-data alarms and operator reconciliation are mandatory.
Alerts dedup by set of checkIDs, resend after6h while unresolved, recovery when clear.
Only successfully accepted notifications advance delivery state; failures retry.
SNS optional for local/manual checks but exit2 until configured. Private state directory,
atomic markers, flock; malformed state fails closed. External observer must alert on
missing monitor heartbeat/nonzero service exits: a failed host cannot alert itself.
No external observer/CloudWatch alarm is installed by this patch. This remains a gate.

S3 RESUME RECOVERY / ERASURE PROPOSAL — NOT IMPLEMENTED
Current UUID object keys avoid routine overwrite. Transactional cleanup outbox retries
default_storage.delete and protects live references. It does NOT enumerate/delete
historical S3 versions. Enabling versioning alone would make erasure incomplete.
Propose30-day noncurrent version retention, private encryption unchanged, no ObjectLock.
Accidental delete: identify exact key/version under incident approval, reconcile DB
reference, then restore selected version without overwriting unrelated files. If DB
record was deleted, object recovery alone does not recover profile/authorization.
Erasure: revoke access first; journal exact keys; paginate all versions/delete markers
for each exact key; delete with retry/verification, including approved recovery copies.
Use separately approved minimal version-management permissions; do not use prefix-wide
deletion or give public API broad bucket permissions. Implement/test before versioning.
Backup retention may retain erased rows until expiry; document legal basis, restricted
restore use and apply durable erasure ledger after any recovery before enabling access.
No erasure ledger implemented by this patch. Approve legal retention policy first.

cleanup. Restore previous ops scripts/env/units and daemon-reload; application images,
database, resumes, queues and network remain unchanged. Keep retained S3 backups.
