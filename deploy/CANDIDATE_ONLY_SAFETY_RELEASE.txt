Controls
APP_ENV=production + CANDIDATE_ONLY=true disables recruiter permission checks,
including password login, existing tokens/cookies and recruiter resume downloads.
Middleware denies recruiter paths and recruiter API families with 404. Candidate
login/profile/preview remain available. The flag is ignored outside production.
Build frontend with VITE_CANDIDATE_ONLY=true: remove recruiter navigation/login
choice without layout/copy changes and deny /recruiter and descendants in nginx.
Use both backend and frontend controls; navigation alone is NOT security.

CANDIDATE_REGISTRATION_PAUSED=true denies signup POST (503, Retry-After 3600).
RESUME_UPLOADS_PAUSED=true denies new resume/retry POST. Existing auth, verification,
reset, saved profile, polling and queued/running jobs remain untouched. These are
environment-based controls requiring backend recreation to change; they are not
instant live toggles. Worker code does not read them. Do not recreate worker for
an emergency intake toggle. Proxy-level temporary POST denial can pause intake
without a backend restart; it requires separately reviewed Caddy configuration.

Backup installation proposal (requires separate approval)
1. Preserve current ops.env, service units and config. Verify exact account,
   instance, region, private encrypted bucket and existing role upload/read rights.
2. Install deploy/backup_safe.py and wrappers, NOT the old live-container restore.
   Host needs python3+boto3, aws CLI with IfNoneMatch/ChecksumSHA256, Docker, flock.
   Create /var/lib/enter-ops mode0700 and configure launch-controls.env.example
   operational variables in existing /etc/enter/ops.env (never copy example secrets).
3. Run backup.sh manually once before timers. It uses consistent pg_dump,
   unique UUID keys, conditional upload If-None-Match *, AES256 and SHA256 readback.
   It restore-tests EVERY backup with exact existing PostgreSQL image, network none,
   no ports/live mounts, 0.5 CPU, 768MiB memory, 384MiB tmpfs. No image pull.
   pg_amcheck validates restored structure. Success removes only unique scratch
   resources; failure retains mode0700 files/container for operator investigation.
   Do not blindly run rm/prune. Never restore a backup onto live data for code rollback.
4. Explicit safe limits: database <50MiB, available RAM >3GiB, free disk >5GiB.
   These conservative staging-proven limits must be reassessed with measured growth;
   do not silently raise them. Concurrent writes are reported, not prohibited:
   pg_dump is a consistent snapshot and is not the latest state after it finishes.
5. Install enter-backup.service/timer (hourly) and enter-backup-daily.service/timer
   (02:15 UTC daily); enable only after approval. Shared flock prevents overlaps.
   Both update a private atomic success marker only after restore verification.
6. Proposed backup-retention.proposed.json: hourly prefix expires after7 days;
   daily prefix expires after30 days. This is destructive lifecycle expiration,
   NOT applied by scripts. Read and merge existing bucket rules before approved
   application; never overwrite unrelated rules. Old postgres/YYYY keys are outside
   these prefixes and remain untouched. Set retention days by reviewed JSON change.
   Keep bucket versioning status in review: noncurrent versions require separate rules.
7. Monthly independent recovery drill should choose an older retained object,
   verify archived checksum and restore offline, record duration and usable schema.
   Current restore-test.sh makes/verifies a fresh backup; it does NOT independently
   test a historical snapshot or application reconciliation. Historical drill remains
   an operator procedure requiring a reviewed scratch-only script and selected key.
   Proposed RPO <=1 hour / RTO <=4 hours are goals, not measured guarantees.

backups alone cannot recover deleted objects. Approve either versioned recovery
with bounded noncurrent retention or a separate encrypted recovery copy. Do not
