Design
------
Lambda enter-public-https-monitor outside VPC, Python 3.12, 128 MiB, 30s timeout.
EventBridge Scheduler enter-public-https-monitor in a dedicated same-named
schedule group, every five minutes. No flexible window or Scheduler retries.
CloudWatch namespace ENTER/PublicAvailability; metric Healthy (Count, no
dimensions); alarm enter-public-https-unavailable. Minimum <1, two of two
five-minute periods, missing data breaching. ALARM and OK actions use:
arn:aws:sns:ap-southeast-2:431988153216:enter-production-alerts
Notifications are state transitions, not an email on every failed probe.
Both schedule and alarm actions are DISABLED at installation.
No endpoint can be selected by invocation input. Current reviewed host is
staging.enter.careers. A production hostname requires a reviewed code change.

GET / must return 200, HTML and the existing React root marker. GET
/api/v1/health/ready/ must return 200 JSON status=ready and database=ok.
These are availability checks, not browser rendering or complete worker checks;
the existing on-server monitor continues checking queues/scanner/worker/backups.
Both requests use public IPv4 DNS, connect to a validated public IP, preserve
Host/SNI, and verify TLS using the system CA store. No proxy, redirects,
credentials, cookies, private DNS addresses, local overrides or auth requests.
Only bounded bodies are examined in memory; none are logged or persisted.
Logs/return values contain fixed fields and booleans. Raw exception text and
invocation events are never logged. A stalled invocation times out; absent
metrics are alarm failures. IPv6-only hosting is not supported by this version.
This survives EC2 loss but is not independent of Sydney/AWS/account failure.

NETWORK BLOCKER: current staging ingress is restricted to authorized IPs.
Non-VPC Lambda does not have a fixed egress address suitable for that allowlist.
Do not change ingress, create NAT/EIP, or use loopback to manufacture success.
Keep scheduling disabled until a separately approved public-access/cutover
plan makes the reviewed endpoint genuinely reachable from the probe.

  cloudwatch:PutMetricData Resource * with StringEquals:

  logs:CreateLogStream, logs:PutLogEvents on:
    arn:aws:logs:ap-southeast-2:431988153216:log-group:/aws/lambda/enter-public-https-monitor:log-stream:*

ENTER-PublicHttpsScheduler-Role trusts scheduler.amazonaws.com, conditioned on
aws:SourceAccount=431988153216 and aws:SourceArn equal to the dedicated
arn:aws:scheduler:ap-southeast-2:431988153216:schedule-group/enter-public-https-monitor

Its only action is lambda:InvokeFunction on:
arn:aws:lambda:ap-southeast-2:431988153216:function:enter-public-https-monitor

SNS policy addition: CloudWatch service principal, sns:Publish only on the
existing topic, SourceAccount=431988153216, SourceArn exact alarm ARN.

the existing topic policy. No SNS permission is added to either runtime role.

Supervised installation AFTER separate approval
-----------------------------------------------
1. Verify account/region, artifact checksums, no conflicting same-named
   resources, public reachability plan, and installed-role policy documents.
2. Prepare an unexecuted change set using the reviewed template hash:
   ENTER_APPROVE_MONITOR_CHANGE_SET=431988153216/ap-southeast-2 \
     bash deploy/public_monitor_change_set.sh /private/tmp/enter-public-monitor-review APPROVED_TEMPLATE_SHA256
   This creates a CloudFormation change set only. It is NOT a local dry run.
3. Inspect all additions and permission changes:
   aws cloudformation describe-change-set --region ap-southeast-2 \
     --stack-name enter-public-https-monitor --change-set-name REVIEWED_CHANGE_SET_NAME
   Require only the seven declared monitor resources. No existing resource
   replacement and no EC2/SNS topic/S3/network changes.
4. With explicit execution approval:
   aws cloudformation execute-change-set --region ap-southeast-2 \
     --stack-name enter-public-https-monitor --change-set-name REVIEWED_CHANGE_SET_NAME
   aws cloudformation wait stack-create-complete --region ap-southeast-2 \
     --stack-name enter-public-https-monitor
5. Verify Scheduler DISABLED, alarm ActionsEnabled=false, log retention,
   exact roles, function source and absence of VPC configuration.
6. Inspect SNS topic attributes. Back up the current policy. Merge the exact
   reviewed statement, preserving every existing statement; compare the latest
   policy again immediately before writing. Stop on concurrent differences.
   The setter is intentionally not automated. Verify the resulting policy.
7. When public reachability has separately been approved, invoke once:
   aws lambda invoke --region ap-southeast-2 --function-name enter-public-https-monitor \
     --payload '{}' --cli-binary-format raw-in-base64-out /private/tmp/enter-public-monitor-result.json
   Require metric_published=true, frontend=true, readiness=true and Healthy=1.
   Do not treat successful Lambda invocation alone as successful HTTPS checks.
8. Separately approve activation. Update the stack with Schedule State=ENABLED
   and alarm ActionsEnabled=true through a reviewed UPDATE change set, changing
   only those two properties. Retain the disabled template as rollback.
   Confirm two successive samples, and test notification ALARM -> OK using
   SetAlarmState with a synthetic reason on this alarm only. Request inbox
   confirmation of both messages. Do not stop EC2 or break application services.
   A supervised disabled-schedule drill (about 10-15 minutes) must verify missing
   data detection and subsequent recovery; promptly restore its approved state.
   State-forcing alone does NOT prove missing-data evaluation works.
9. Record actual artifact hash, stack/resource ARNs, delivery receipts, timing,
   public DNS/TLS results and any failed checks. Not tested until performed.

Rollback/emergency
------------------
Use a reviewed UPDATE change set reverting Schedule State=DISABLED and alarm
ActionsEnabled=false. Preserve EC2 monitoring, data, application and SNS topic.
Do not delete the shared SNS topic or replace its whole policy. If removing
the installation later, remove only this exact policy statement after review.
Do not use stack deletion as the default incident response.
